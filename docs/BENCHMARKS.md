# Benchmarks

All numbers below were **measured**, not estimated, by `backend/scripts/benchmark.py` on 2026-11-19.

## Method

- **Input:** nine synthetic 30-second stereo files with known damage, generated by
  `python scripts/benchmark.py --synthetic`. No copyrighted audio. The base signal is stereo
  noise with a pink (-3 dB/octave) tilt and drum-like transients. It is a stand-in for music, not
  music, and is about 13 dB peak-to-loudness, like a typical mix.
- **Pipeline:** `enhance()` exactly as the worker runs it, with the Spotify profile
  (-14 LUFS, -1 dBTP), at 48 kHz and 24-bit.
- **"Before"** is the gatekeeper on the input. **"After"** is the gatekeeper run again on the
  delivered 24-bit WAV, and the output true peak is measured with 16x oversampling.
- **Machine:** Apple M4 (10 cores), macOS, Python 3.11.15. The default device was `mps`.
  **AudioSR was not available.**
- **Reproduce:** `cd backend && python scripts/benchmark.py --synthetic --no-env`

The same set on **CPU only** (`COMPUTE_DEVICE=cpu`) took 1.29–1.35 s per 30-second file, about
22–23x real time, so it was slightly faster than MPS. The DSP path is numpy/scipy work, such as
oversampled true peak and the STFT, so a GPU doesn't speed it up. A GPU only matters for AudioSR.

## What the numbers show

- **Loudness and peaks:** every track with signal landed at -14.0 LUFS (the target is reached
  within 0.1 LU by design) with a true peak at or below -1.19 dBTP. The test suite separately
  checks the same guarantee with an **independent 32x-oversampled meter**, in
  `tests/test_mastering.py`.
- **Gatekeeper bypass:** clean, 16 kHz-cutoff and quiet files skipped all repair.
  - The 16 kHz file is reported as a likely good-quality lossy source (info only), by design: the
    spec's limit is a cutoff below 15 kHz.
  - The 85% spectral rolloff is still reported, but it doesn't drive the decision. It flags most
    normal music.
- **De-clipping:**
  - Flat-topped samples dropped to 0.000% on the delivered WAV.
  - Case 03 ("clipped, then turned down 3 dB") is detected because flat tops are measured
    against the file's own peak. With an absolute 0.99 threshold (the earlier version), it
    scored 100 A with no clipping found.
  - In the unit tests, the spline repair reduced the error against the known original by about
    14 dB (3 dB clip) and 7 dB (6 dB clip) on bass and chord peaks. It made no measurable
    difference on noise-like transients.
- **Missing high frequencies:** cases 05, 06 and 08 were flagged correctly. Without AudioSR they
  were only resampled, and the job is marked **partial**, with the note "High frequencies were not
  restored: the AI model is not installed on this server".

\* **Case 06 needs care.** Its after-analysis reports a 21.0 kHz cutoff and a 100 A score.
Those highs were **not** restored. De-clipping adds broadband energy above the original 11 kHz
cliff, so the cliff detector no longer finds a 20 dB drop. That energy is a by-product, not
music. The product does not present it as an improvement: the job outcome is `partial`, and the
dashboard's "after" value for high frequencies says **"Not restored"** instead of the measured
number. The re-run score is not used anywhere in the product; it is shown here only for completeness.

## Not measured (yet)

- **AudioSR quality and speed.** It needs a CUDA host. Our adapter feeds it 5.12 s chunks (AudioSR's
  recommended segment length) with 50 diffusion steps, and its real-time factor on a given GPU must be
  measured before any cost or latency claim.
- **Real music and listening tests.** Run `python scripts/benchmark.py path/to/folder` on tracks
  you have rights to (for example, Pixabay-licensed music) and add blind A/B listening before
  claiming perceptual improvement.
- **Throughput under concurrency.** These are single-process, one-file-at-a-time timings.
